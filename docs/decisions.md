# Решения

| # | Решение | Причина |
|---|---|---|
| D1 | Данные взяты из зеркала `microsoft/hnm-search-data` (Hugging Face), SHA-256 сверены с LFS-метаданными зеркала | Kaggle требует авторизации и принятия правил; зеркало публично. Условия использования — исходные правила соревнования |
| D2 | PostgreSQL 16.8 в Docker на `127.0.0.1:55432` | порт 5432 на машине занят локальным PostgreSQL; доступ только с localhost |
| D3 | Загрузка transactions: Python читает файл построчно, добавляет `load_id,src_row` и передаёт поток `COPY FROM STDIN` в UNLOGGED staging; типизация — `INSERT … SELECT` с регулярными проверками | контейнер не видит Windows-пути; ошибки типов изолируются построчно, а не обрывают всю загрузку |
| D4 | Проверка дат через таблицу различных строк `t_dat` (734 значения), разобранных в Python | невозможные даты (`2019-02-30`) не вызывают ошибку приведения в SQL |
| D5 | customers/articles разбираются модулем `csv` | в `articles.csv` есть экранированные поля с запятыми |
| D6 | Идемпотентность: повторный ingest файла с тем же SHA-256 переиспользует завершённую загрузку; `--mode replace` удаляет только партицию этой загрузки | исключает удвоение покупок; нет UNIQUE по содержательным полям |
| D7 | Партиционирование raw по `load_id`, derived по `dataset_id` | перестроение затрагивает ровно одну загрузку/набор; smoke и full не смешиваются |
| D8 | `customer_sk` = ранг `customer_id` (COLLATE "C") внутри набора | детерминированно, обратимо через `derived.customer_key` |
| D9 | Smoke: `int(sha256("hmrp-sample-v1:" + customer_id)[:8], 16) % 10000 < 100` | стабильный хеш, не зависит от порядка строк и соли Python |
| D10 | `observation_end_exclusive = max(t_dat) + 1`, если нет пропущенных дат и последний день ≥ 0.5 медианы предыдущих 28 дней | проверка обрезки файла по объёму последнего дня; фактическое решение записано в `dataset_summary.json` |
| D11 | Признаки срезов считаются из `customer_day` по одному cutoff за запрос, с индексом `(t_dat, customer_sk)` | нет декартова произведения raw × cutoff; каждая дневная строка читается ≤ 4 раза |
| D12 | EXPLAIN ANALYZE выполняется для `customer_day` и первого среза в рамках самой сборки | не удваивает тяжёлые вычисления |
| D13 | Метки строятся SQL-ом для всех допустимых cutoff; доступ к меткам test-среза в Python — только из `evaluate` | служебное построение отделено от доступа обучения |
| D14 | Early stopping CatBoost — по validation текущего fold (по заданию) | следствие: оценка CatBoost на dev слегка оптимистична относительно LR; в final refit число деревьев фиксировано заранее |
| D15 | Во всех моделях `ranking_source = raw_score`; основная вероятность — `calibrated_probability` | контракт зафиксирован в `selection_decision.json` до test |
| D16 | Platt на 1-D `raw_score` без регуляризации | простое монотонное преобразование не меняет ранжирование |
| D17 | Tie-break — `sha256("hmrp-tie-v1:" + customer_id)` | детерминирован, не зависит от target и будущего |
| D18 | LR-extended — диагностика (не кандидат) | позволяет отделить эффект признаков от эффекта алгоритма, не меняя заранее заданный приоритет кандидатов |
| D19 | CatBoost CPU, 16 из 24 логических потоков; PostgreSQL до 4 параллельных воркеров; тяжёлые этапы последовательно | первая попытка full с 8 потоками дала 196 с на одну CatBoost-конфигурацию (8.2 млн строк); остановлена до завершения fold 1 и перезапущена с 16 потоками без изменения сетки; GPU не требуется |
| D20 | Отчёты и блоки README генерируются `hmrp report` из JSON/CSV run | числа не правятся вручную |
| D21 | `sales_channel_id` используется только как доля записей канала 2 | смысл кодов источником не раскрыт |
